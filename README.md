# Snippet Stack

Личное веб-приложение для хранения фрагментов кода и команд терминала. Python 3.12, Django 5.2 LTS, SQLite, Gunicorn и WhiteNoise. Frontend — серверные HTML-шаблоны, CSS и небольшой vanilla JavaScript, без npm, CDN и внешних шрифтов.

## Возможности

- Регистрация, вход, выход; приватная библиотека для каждого пользователя.
- Создание, редактирование, удаление с подтверждением, избранное и копирование полного кода.
- Теги через запятую, поиск по названию, описанию, коду и тегам, фильтрация по языку, сортировка и пагинация.
- Отдельный раздел терминальных команд; код никогда не исполняется сервером.
- Адаптивная сетка и мобильная навигация, светлая и тёмная темы с сохранением выбора.
- Редактор: Tab для отступа, Ctrl/⌘ + Enter для сохранения, предупреждение о несохранённых изменениях; `/` фокусирует поиск.
- PWA manifest, PNG-иконки и service worker. Установка поддерживается совместимыми браузерами на HTTPS или localhost. Офлайн доступна страница отсутствия соединения, личные данные не кэшируются и редактирование без сети не поддерживается.

## Быстрый запуск Docker

Нужен работающий Docker Engine / Docker Desktop с Compose v2.

```sh
cp .env.example .env
python3 -c "import secrets; print(secrets.token_urlsafe(64))"
```

Вставьте сгенерированное значение в `SECRET_KEY` файла `.env`, затем:

```sh
docker compose up --build -d
```

Откройте http://localhost:8000 и создайте аккаунт. Миграции выполняются при старте. Данные хранятся в именованном volume `snippet_data` и сохраняются при обновлении контейнера.

```sh
docker compose logs -f web
docker compose down
```

`docker compose down -v` удалит базу вместе с volume — не используйте эту команду для обычного обновления.

## Локальная разработка

Python 3.11+:

```sh
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
export SECRET_KEY="$(python3 -c 'import secrets; print(secrets.token_urlsafe(64))')"
export DEBUG=true
python manage.py migrate
python manage.py runserver
```

Прямой запуск Django не читает `.env` автоматически: используйте переменные окружения. SQLite находится в `data/db.sqlite3`. Секреты, база, виртуальное окружение и собранная статика исключены из Git и Docker build context. В репозитории нет встроенных аккаунтов и паролей.

## Развёртывание на сервере

Порт по умолчанию опубликован только на `127.0.0.1`. Поставьте перед ним HTTPS reverse proxy (Caddy / Nginx), добавьте домен в `ALLOWED_HOSTS` и полный origin в `CSRF_TRUSTED_ORIGINS`. Сохраните `127.0.0.1` в `ALLOWED_HOSTS` для healthcheck.

```dotenv
ALLOWED_HOSTS=snippets.example.com,localhost,127.0.0.1
CSRF_TRUSTED_ORIGINS=https://snippets.example.com
HTTPS=true
TRUST_PROXY=true
```

Включайте `TRUST_PROXY` только когда доверенный reverse proxy **перезаписывает**, а не просто передаёт клиентский `X-Forwarded-Proto`, и прямой доступ к backend закрыт. Для Nginx: `proxy_set_header Host $host;` и `proxy_set_header X-Forwarded-Proto $scheme;`. Ограничьте размер тела запроса до 256 KiB, частоту регистрации и входа на proxy. Настройте реальный адрес клиента для django-axes, если используете proxy; по умолчанию ограничение применяется к IP прямого соединения, поэтому клиенты за одним proxy могут разделять блокировку.

При `HTTPS=true` включаются secure cookies, HTTPS redirect и HSTS. Исключение `/health/` возвращает только состояние доступности БД. Проверка настроек production:

```sh
docker compose exec web python manage.py check --deploy
```

Защита приложения: Django ORM, стандартное хеширование и валидация паролей, CSRF, автоматическое экранирование, проверка владельца каждой записи, строгий CSP, HttpOnly session cookie, запрет встраивания во frame, отсутствие исполнения сниппетов. После 5 неудачных попыток входа IP блокируется на 15 минут (состояние в БД, общее для workers). Регистрация открытая. Восстановление пароля по email и MFA не входят в текущую реализацию.

Контейнер работает без root и Linux capabilities. `DEBUG` в Compose выключен. Зависимости зафиксированы в `requirements.txt`; регулярно обновляйте security-патчи. SQLite подходит для личной библиотеки и небольших команд; записи сериализуются, поэтому для высокой конкурентной нагрузки потребуется переход на PostgreSQL и повторная проверка запросов/миграций.

## Резервная копия SQLite

Создавайте согласованную копию через SQLite backup API:

```sh
docker compose exec web python -c "import sqlite3; source=sqlite3.connect('/app/data/db.sqlite3'); target=sqlite3.connect('/app/data/backup.sqlite3'); source.backup(target); target.close(); source.close()"
docker compose cp web:/app/data/backup.sqlite3 ./backup.sqlite3
```

Копия содержит приватный код и хеши паролей: храните её вне публичного доступа. Для восстановления остановите приложение, замените `db.sqlite3` в volume копией, сохранив права пользователя контейнера, затем запустите сервис. Перед обновлением делайте backup.

## Гибридный поиск: BM25 + векторы + RRF

Строка поиска принимает обычную фразу, например `убить процесс на порту 8080`.

1. **SQLite FTS5 / BM25** ищет по названию, описанию, всему коду и тегам. Веса колонок: 4 / 2 / 1 / 3. Токены объединяются через OR с поиском по префиксу; операторы FTS из пользовательского ввода не исполняются. Это поиск по словам, не морфологический анализ русского языка.
2. **FastEmbed / ONNX Runtime на CPU** кодирует запрос моделью `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2` (384 измерения). Мультиязычный вариант выбран для запросов на русском к английским описаниям. Заголовок, описание, теги и код формируют текст документа; длинные документы обрезаются до окна модели, тогда как FTS индексирует весь код. Краткое описание назначения команды существенно улучшает смысловой поиск.
3. **Cosine similarity** сравнивает нормализованные векторы только доступных пользователю сниппетов, уже с применёнными фильтрами. Используется точный поиск NumPy пакетами по 256 векторов, без отдельного сервера и ANN-расширений. Он имеет линейную сложность по размеру отфильтрованной библиотеки; для миллионов записей потребуется другой векторный индекс.
4. **RRF** объединяет до 100 кандидатов каждой ветки: `score(d) = sum(1 / (60 + rank(d)))`, ранги начинаются с 1. В выдаче до 200 кандидатов, по умолчанию в порядке релевантности. Сортировку по названию/дате можно выбрать отдельно — она применяется к найденным кандидатам. Порог cosine по умолчанию 0.25 — эвристика для отсечения слабых совпадений, а не вероятность правильного ответа.

Векторы хранятся в той же SQLite. Поиск не запускает LLM, не исполняет команды и не отправляет код/запросы внешнему API. Модель загружается один раз из Hugging Face фоновым процессом и сохраняется в `data/models` (в Docker — внутри постоянного volume). Первый запуск требует интернета, свободного места под модель и может занять несколько минут. Web workers используют только локальные файлы: загрузка модели не происходит внутри HTTP-запроса. Модель лениво загружается в память каждого worker; первый смысловой запрос медленнее последующих. Повторные векторы запросов кэшируются в памяти worker (до 128 строк).

### Запуск и обновление индекса

`docker compose up --build -d` запускает `web` и фоновый `search-indexer`. Индексатор стартует после миграций и успешного healthcheck web. Он проверяет новые/изменённые записи каждые 3 секунды, считает векторы вне транзакции и сохраняет результат только если исходный текст не изменился за время вычисления. Лексический индекс обновляется сразу, вместе с изменениями сниппета/тегов. При отсутствии модели или ошибке inference остаётся поиск по словам, а интерфейс показывает состояние смыслового поиска.

```sh
docker compose logs -f search-indexer
# Восстановить индекс после bulk-импорта/QuerySet.update(), обходящего сигналы:
docker compose exec web python manage.py index_search --rebuild
```

Для локальной разработки (то же окружение `SECRET_KEY` и `DATA_DIR`, что у web):

```sh
python manage.py migrate
python manage.py index_search          # скачать модель и обработать текущие сниппеты
python manage.py index_search --watch  # оставить в отдельном терминале
```

`SEARCH_SEMANTIC_ENABLED=false` отключает смысловую ветку. `SEARCH_THREADS=2` ограничивает число потоков ONNX на процесс. Фактическая задержка зависит от CPU, длины текста, числа сниппетов и прогрева; фиксированные 20 мс не гарантируются. В production учитывайте, что каждый Gunicorn worker и индексатор держат свою модель в памяти.

Для настройки порога задайте `SEARCH_MIN_SIMILARITY` в окружении обоих сервисов (при необходимости добавьте переменную в Compose). При смене модели/алгоритма эмбеддинга нужно пересчитать все векторы через `index_search --rebuild`, не смешивая пространства. В данной версии модель фиксирована в настройках.

Дополнительные тесты проверяют BM25, экранирование FTS-запросов, RRF, фильтрацию до top-k, изоляцию пользователей, обновление/удаление тегов, инвалидацию векторов, восстановление после bulk-операций, fallback и гонку между редактированием и индексированием. Они не скачивают модель; качество реального encoder проверяется отдельно.

Источники: [SQLite FTS5](https://www.sqlite.org/fts5.html), [модели FastEmbed](https://qdrant.github.io/fastembed/examples/Supported_Models/).

Проверка настоящей модели после её загрузки:

```sh
RUN_SEMANTIC_TESTS=1 python manage.py test snippets.test_search
```

Она создаёт изолированную тестовую БД, индексирует английские команды, проверяет русские запросы с портом и без лексических совпадений через весь путь BM25 → cosine → RRF → страница результатов. Обычный запуск тестов пропускает только этот тест.

При локальной проверке на небольшом корпусе из 6 сниппетов запросы «убить процесс на порту 8080» и «освободить занятый порт» вернули `lsof -ti:8080 | xargs kill -9` первым. Кодирование прогретых запросов заняло примерно 3–4 мс; загрузка модели и кодирование корпуса — около 600 мс. Это smoke-проверка на машине разработки, не нагрузочный benchmark или гарантия latency.
